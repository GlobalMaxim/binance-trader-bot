# Impact Analysis: Removing SELL Entry Logic

## What SELL signals actually do today

SELL signal has two outcomes, determined by portfolio state at dispatch time:

| Portfolio state | Path | Result |
|---|---|---|
| No open position | `evaluate_sell()` → REJECTED / NO_OPEN_POSITION | Signal + decision written to DB. Nothing traded. |
| Long position open | `evaluate_sell()` → APPROVED | Market sell order executes. Long closed. Exit tagged "strategy_exit". |

The first path is zero-value compute waste. The second path is a genuine exit mechanism that overlaps with `check_exit()`.

## 2. What improves

### Signal stream becomes honest

Today the signals table contains BUY, SELL, and HOLD rows. SELL rows are misleading — they suggest the strategy is bi-directional. After removal, only BUY and HOLD exist. Every BUY is potentially actionable. The signal stream matches system capability 1:1.

### Decision table becomes diagnostic

Today the decisions table accumulates REJECTED/NO_OPEN_POSITION rows that are not failures — they're the correct behavior for a long-only system seeing a SELL signal. Every analytics query that computes rejection rate must filter them out. After removal, every REJECTED decision is a real problem (NOTIONAL_TOO_LOW, INSUFFICIENT_BALANCE, MAX_POSITIONS). The rejection rate becomes a useful health metric.

### Compute waste eliminated

`_trend_sell()` and `_range_sell()` evaluate indicator conditions on every bar for every symbol. This is pandas operations on the full DataFrame — not zero-cost. For a system running 10 symbols on 1m bars, that's 600 evaluations per hour of logic whose output is always discarded.

### Architecture matches capability

A developer reading `generate_signals()` today sees four entry functions and reasonably concludes the system trades both directions. It doesn't. After removal, the code says what it does: generate BUY signals, exit via `check_exit()`. No false advertising.

## 3. What breaks (and how to fix)

### Range overbought exit is lost

`_range_sell()` fires when: RANGE regime + RSI >= 68 + near BB upper + MACD peak + volume OK. This exit condition has no equivalent in `check_exit()`.

Why this matters: a long entered during RANGE at BB lower (via `_range_buy`) relies on the mean-reversion sell signal to close at the upper band. Without it, the position stays open until SL, TP, or TIME_EXIT fires. The entire range mean-reversion strategy becomes entry-only — it buys the dip but never sells the rip systematically.

**Fix:** Add MEAN_REVERSION exit reason to `check_exit()`. Condition: `regime == RANGE AND rsi >= range_rsi_overbought`. This requires passing RSI into `ExitCheckInput`. One new field, one new check line, zero new functions. The condition moves from signal generation to exit checking, which is where it belongs — it was always an exit condition misclassified as an entry signal.

### Trend sell exit shifts from leading to lagging

`_trend_sell()` fires when: TREND_DOWN regime + price near EMA + MACD peak + volume. `check_exit()` has REGIME_FLIP which fires once when regime changes to TREND_DOWN. These overlap but aren't identical:

- REGIME_FLIP: fires once at the moment regime flips. One-shot.
- Trend sell: fires repeatedly whenever price touches EMA during a downtrend. Multi-shot.

The practical difference: after REGIME_FLIP fires (closing the long), if the position was already closed by REGIME_FLIP, trend sell is irrelevant. If REGIME_FLIP hasn't fired yet (regime still reading TREND_UP due to ADX lag), trend sell might fire first — but that's a false signal caused by the same ADX lag.

Net: REGIME_FLIP is sufficient. The trend sell's "multi-shot" property sounds useful but in practice it fires on ADX-noise regime misclassifications. Losing it is neutral or slightly positive.

### Signal.SELL becomes a zombie enum

The enum value `Signal.SELL = "SELL"` remains defined but never generated by `generate_signals()`. Existing DB rows with `signal='SELL'` still query fine. New code won't produce them.

**Fix:** Keep the enum. Removing it would break any code that imports `Signal.SELL` (even if that code is never reached). Zombie enums are harmless. Add a comment: `# SELL unused — long-only system, exits via check_exit() only`.

### EVT_STRATEGY_EXIT becomes unreferenced

The constant exists in `log_repo.py` and is imported in `trading_engine.py` but never written to bot_logs. Existing log rows tagged "strategy_exit" remain queryable.

**Fix:** Keep the constant. Removing it breaks nothing but provides zero value. Historical data integrity is worth a one-line zombie.

## 4. Option comparison

### Option A: Keep SELL signals, never act on them (current state)

| Pro | Con |
|---|---|
| Zero code changes | Analytics permanently polluted |
| _range_sell exit still works | Every dashboard query needs `reject_reason != 'NO_OPEN_POSITION'` filter |
| Future short support has template code | New developers confused by dead paths |
| | Compute wasted every tick |
| | Architecture lies about capability |

### Option B: Remove SELL entry, preserve exit condition in check_exit

| Pro | Con |
|---|---|
| Clean signal stream (BUY/HOLD only) | Must add MEAN_REVERSION to check_exit (3-line change) |
| Decision table shows only real rejections | Signal.SELL becomes zombie enum |
| No compute waste on dead paths | _trend_sell/_range_sell templates lost (recoverable from git) |
| Architecture matches actual capability | |
| Fewer code paths to test and debug | |
| Exit logic consolidated in one place (check_exit) | |

The "cons" for Option B are all one-time, trivial, or recoverable. The "cons" for Option A are ongoing and compound over time.

---

## 5. Recommendation: REMOVE

### Reason 1: The only valuable SELL condition (range overbought) belongs in check_exit, not in signal generation

`_range_sell()` is semantically an exit check — "close long because RSI is overbought in a range." It was shoehorned into signal generation because the original architecture didn't have an exit engine. Now that `check_exit()` exists and handles five exit conditions, the range overbought condition should move there. This isn't removal — it's relocation to the correct layer.

### Reason 2: Dead signal paths destroy observability

A trading system lives or dies by its ability to answer "what happened and why." Every SELL→REJECTED row is noise that obscures real problems. When rejection rate spikes, is it because NOTIONAL_TOO_LOW is firing (real problem) or because the market is trending down (expected NO_OPEN_POSITION)? Without removing the dead path, you can't tell without manual filtering.

### Reason 3: Trend sell is redundant with REGIME_FLIP

`_trend_sell()` and REGIME_FLIP target the same scenario: long should close because trend turned bearish. REGIME_FLIP is the cleaner mechanism — it's systematic, auditable, and fires at the regime transition boundary. Trend sell is a noisy duplicate that fires on false regime readings from ADX lag. Two mechanisms for one exit condition is one too many.

### Reason 4: The system needs to prove long-only profitability before going multi-directional

Adding shorts doubles the surface area for bugs, calibration errors, and losing trades. The system can't be profitable in both directions if it can't be profitable in one. Removing SELL entry forces focus on what matters: making the long side work (fix ADX lag, calibrate SL for 1m noise, activate range mode). Shorts come later — and when they do, the exit engine (`check_exit`) already handles both directions via the `direction` parameter.

### Reason 5: Re-adding is trivial, re-understanding is not

`_trend_sell()` and `_range_sell()` are 12-line functions recoverable from git in 30 seconds. The hard part of short selling — portfolio tracking, risk gating, inverted exit checks, direction-flip transitions — is unaffected by this removal. What's NOT trivial is a new developer spending hours tracing why SELL signals exist but never trade. That confusion cost is paid every time someone reads the code. Remove it once, save it forever.
